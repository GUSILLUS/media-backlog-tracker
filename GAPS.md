# GAPS.md — план закриття фідбеку зі співбесіди

Джерело: фідбек після backend-інтерв'ю (вересень 2026).
Формат такий самий, як PROGRESS.md: пишу код я, Claude рев'ює і пояснює.

**Правило блоку:** блок не закритий, поки я не написав своїми словами відповідь
на його «Маю пояснити» (~150 слів, вголос, як на співбесіді) і не отримав критику
саме на пояснення, а не на код.

Порядок нижче — це порядок **будування проєкту**, а не порядок пунктів фідбеку.
Теорія приходить разом із кодом, який її потребує.

## Блок 0 — борг з Day 3 (закрити першим, це блокує все інше)

Ще не зроблено з ревʼю в PROGRESS.md, і це видно прямо в схемі:

- [ ] `User.password` досі називається `password`, а не `passwordHash`. Назва поля —
      це документація: `password` провокує когось колись покласти туди plaintext.
- [ ] `Media.user` не має `onDelete`. Prisma за замовчуванням ставить `Restrict` для
      обовʼязкового звʼязку → **видалити юзера з медіа зараз неможливо**. Ти цього не
      обирав, воно просто сталося. Це рівно пункт 1 фідбеку (referential integrity).
- [ ] Стрип `passwordHash` з відповідей, однакова помилка на login, `P2002` → 409.

Не йди далі, поки це не полагоджено: наступні блоки міняють ту саму схему.

## Блок 1 — Реляційна модель і цілісність даних
**Фідбек: пункт 1**

### Що додаю в проєкт

1. **Many-to-many з payload.** Додати `Tag` (жанри: horror, roguelike, shonen…) і
   звʼязок `Media ↔ Tag`.
   - Спочатку зробити **implicit m2m** у Prisma (`tags Tag[]` / `media Media[]`),
     подивитись `prisma migrate dev` і прочитати згенерований SQL: Prisma сама
     створила проміжну таблицю `_MediaToTag` з двома FK і unique-індексом.
   - Потім **переписати на explicit join table** `MediaTag { mediaId, tagId, addedAt, addedBy }`.
     Питання, на яке маєш відповісти сам: чому implicit варіант перестав працювати,
     щойну знадобилась колонка `addedAt`?
   - PK проміжної таблиці: composite `@@id([mediaId, tagId])` чи власний `id`? Обери і
     аргументуй. Обидва варіанти живі, це реальний trade-off.
2. **Три різні поведінки видалення в одному проєкті** — щоб відчути різницю, а не
   прочитати:
   - `User` → `Media`: `onDelete: Cascade` (немає юзера — немає його медіа).
   - `Media` → `MediaTag`: `onDelete: Cascade`.
   - `Tag` → `MediaTag`: подумай, чи `Cascade`, чи `Restrict` (видалення популярного
     тега мовчки чистить звʼязки в тисяч записів — це ок?).
   - Додати `Media.seriesId` → self-relation або окрему `Collection` з `onDelete: SetNull`,
     щоб мати живий приклад третьої дії.
3. **Унікальність на рівні БД:** `@@unique([userId, title])` на `Media`. Це дасть
   і 409 у блоці 6, і привід поговорити про те, що unique constraint — це індекс.
4. **Прочитати кожен рядок міграції.** Відкрити `prisma/migrations/*/migration.sql` і
   пояснити: `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY ... REFERENCES ... ON DELETE CASCADE`.
   Це та сама база без ORM.
5. **Написати 5 запитів руками в SQL раніше, ніж у Prisma.** У Neon SQL Editor:
   - усі медіа юзера зі статусом IN_PROGRESS,
   - медіа з тегом 'roguelike' (JOIN через проміжну),
   - кількість медіа по категоріях (GROUP BY + COUNT),
   - теги, які не використані жодного разу (LEFT JOIN ... WHERE ... IS NULL),
   - середній рейтинг по юзерах, де медіа > 5 (GROUP BY + HAVING).
   Потім порівняти з тим, що генерує Prisma (`log: ['query']` у клієнті).

### Маю пояснити
Коли реляційна БД програє (документній, key-value, часовим рядам) і чому саме для
цього проєкту Postgres. Що таке PK і FK фізично, а не концептуально. Чому проміжна
таблиця — це не «технічний костиль», а сутність. Що зламається, якщо цілісність
тримати тільки в коді сервісу, а не в constraint'ах.

### Ресурси
- **PostgreSQL docs, глава 5 «Data Definition»** — constraints, FK, ON DELETE. Коротко і це першоджерело: https://www.postgresql.org/docs/current/ddl.html
- **PostgreSQL Exercises** — https://pgexercises.com — JOIN'и й агрегації руками, з перевіркою.
- **SQLBolt** — https://sqlbolt.com — якщо pgexercises одразу заважкі.
- *Designing Data-Intensive Applications*, розділ 2 — «relational vs document» саме як
  критерії вибору (це рівно перший пункт фідбеку). Решту книги поки не чіпай.

## Блок 2 — Індекси та ідентифікатори
**Фідбек: пункт 2**

Без даних тут вчитись нема на чому. Спершу — обʼєм.

### Що додаю в проєкт

1. **Seed-скрипт на 200k `Media` і 500 юзерів** (`@faker-js/faker`, батчами по 5–10k
   через `createMany`). Це сам по собі урок: спробуй спочатку 200k окремих `create`
   і заміряй час.
2. **`EXPLAIN (ANALYZE, BUFFERS)` як робочий інструмент.** На кожному кроці:
   - `WHERE userId = ?` — Seq Scan чи Index Scan? Скільки мс?
   - додай індекс → перезаміряй,
   - `DROP INDEX` → перезаміряй ще раз. Побач цифри своїми очима.
3. **Розбери свій наявний індекс `@@index([userId, status, favorite])`.** Питання,
   на які маєш відповісти до того, як щось міняти:
   - Чи допоможе він запиту `WHERE userId = ?` (leftmost prefix)?
   - Чи допоможе `WHERE status = ?` без `userId`? Чому ні?
   - Чи має сенс `favorite` (boolean, 2 значення) третьою колонкою? Чи не краще
     **partial index** `WHERE favorite = true`?
   - Спробуй `CREATE INDEX ... WHERE favorite = true` і порівняй `pg_relation_size`.
4. **Ціна індексу на запис.** Заміряй вставку 20k рядків у таблицю з 1 індексом і з 5.
   Те саме для UPDATE поля, яке входить в індекс, і поля, яке не входить.
5. **Бенчмарк ідентифікаторів — окрема гілка, найцінніший артефакт блоку.**
   Створи 4 таблиці по 500k рядків: `bigserial`, `uuid v4`, `uuid v7`, `ulid`.
   Заміряй: час вставки, `pg_relation_size` таблиці й PK-індексу, час
   `SELECT ... ORDER BY id LIMIT 50`.
   Гіпотеза, яку перевіряєш: чому саме **random** UUID псує B-tree (page splits,
   низька локальність), і чому v7/ULID цю проблему знімають.
   Твій поточний `cuid()` — де він у цій системі координат? Лишати чи мігрувати?
   Рішення запиши як ADR (блок 8).
6. Окремо: чому послідовний `bigserial` у публічному URL — це витік (enumeration,
   «скільки в вас клієнтів»), і чому це аргумент безпеки, а не продуктивності.

### Маю пояснити
Що таке B-tree на пальцях і чому пошук — логарифмічний. Чому індекс на поле з
низькою кардинальністю планувальник проігнорує. Чому індекси прискорюють читання
і сповільнюють запис. Повний trade-off bigserial / UUIDv4 / UUIDv7 / ULID по осях:
розмір, локальність запису, безпека, генерація на клієнті, розподілені системи.

### Ресурси
- **Use The Index, Luke** — https://use-the-index-luke.com — канонічний і безкоштовний.
  Мінімум: «Anatomy of an Index», «The Where Clause», «Clustering Data».
- **PostgreSQL docs: Indexes** — https://www.postgresql.org/docs/current/indexes.html
  (типи індексів, partial, multicolumn, index-only scans).
- **pganalyze blog** — серія про роботу індексів і читання EXPLAIN. Шукай
  «pganalyze index internals», «how to read EXPLAIN ANALYZE».
- Для ID: RFC 9562 (UUID v7 — це вже стандарт), spec ULID на GitHub, і будь-який
  бенчмарк «uuid v4 vs v7 postgres insert performance» — але **свої цифри важливіші**.

## Блок 3 — Криптографічна лабораторія (2–3 години, без фічі)
**Фідбек: пункт 4**

Це не фіча, це `scripts/crypto-lab/`. Ціль — щоб ці слова перестали бути словами.

### Що роблю

1. **Один вхід, чотири виходи.** Скрипт, який бере рядок `"password123"` і друкує:
   `base64`, `AES-256-GCM` (з ключем), `SHA-256`, `bcrypt`.
   Потім спробуй відновити оригінал з кожного. Де вийшло, де ні, і чому.
2. **Своя міні rainbow table.** Візьми топ-10k паролів (список rockyou легко гуглиться),
   порахуй SHA-256 кожного, склади в Map. Тепер «зламай» таблицю з 100 несолених
   хешів. Заміряй, скільки це зайняло — це буде секунди.
   Потім додай унікальну сіль кожному і спробуй ще раз. Ось що робить salt.
3. **bcrypt під капотом.** Виведи повний хеш і розбери його на частини:
   `$2b$12$` + 22 символи солі + 31 символ хешу. Сіль **вже всередині** — тому
   `bcrypt.compare` працює без окремої колонки. Заміряй cost 8, 10, 12, 14 і обери
   свій за ціллю ~250 мс на твоєму залізі. Чому не 20?
4. **JWT руками, без бібліотеки.** Візьми свій токен:
   - розбий по `.`, зроби base64url-decode header і payload — побач, що payload
     **читається будь-ким**;
   - порахуй `HMAC-SHA256(base64url(header) + "." + base64url(payload), secret)`
     через `node:crypto` і порівняй з третьою частиною. Має збігтись;
   - зміни один байт у payload → перевір, що `jwt.verify` падає;
   - зроби токен з `alg: "none"` і перевір, чи твій код його прийме. Це реальна
     історична вразливість (CVE-2015-9235), а не теорія.

### Маю пояснити
Encoding / encryption / hashing — три різні задачі, а не три рівні «захисту».
Чому пароль хешують, а не шифрують (у шифрування є ключ, а ключ можна вкрасти;
і тобі *не потрібно* знати пароль). Що дає salt і від чого саме. Що таке secret і
signature в JWT і що вони НЕ дають (конфіденційності).

### Ресурси
- **OWASP Password Storage Cheat Sheet** — https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html
- **jwt.io** — дебагер токенів, щоб звіряти свої розрахунки.
- **Node `crypto` docs** — https://nodejs.org/api/crypto.html (createHmac, createCipheriv).
- Стаття Auth0 2015 «Critical vulnerabilities in JSON Web Token libraries» — про `alg: none`.

## Блок 4 — Auth v2: сесії, refresh, ротація, CSRF
**Фідбек: пункти 3 і частина 5**

У `package.json` уже стоять `cookie-parser` і `express-rate-limit` — вони тут і
знадобляться.

### Що додаю в проєкт

1. **Таблиця `RefreshToken`**: `id`, `userId`, `tokenHash` (не сам токен!), `expiresAt`,
   `revokedAt`, `replacedById`, `userAgent`, `ip`.
   Питання: чому в БД лежить **хеш** refresh-токена, а не він сам? (Підказка: дамп БД.)
2. **Дві ролі токенів.** Access — 15 хв, у памʼяті фронта, в `Authorization: Bearer`.
   Refresh — 30 днів, у `HttpOnly; Secure; SameSite=Lax; Path=/auth/refresh` кукі.
   Маєш вміти сказати, чому саме така асиметрія, а не один довгий токен.
3. **`POST /auth/refresh` з ротацією**: старий refresh помічається `revokedAt`,
   видається новий, `replacedById` вказує на новий → утворюється ланцюжок (token family).
4. **Reuse detection.** Якщо прийшов уже відкликаний refresh — це або крадіжка, або
   гонка. Правильна реакція: відкликати **весь ланцюг** і змусити перелогінитись.
   Реалізуй і напиши тест, який це відтворює.
5. **`POST /auth/logout`** (відкликати поточний) і **`/auth/logout-all`** (усі сесії юзера).
   Ось тут ти на практиці відповіси, чому «вийти з усіх пристроїв» неможливо зробити
   чесно на stateless JWT без такої таблиці.
6. **Гілка `feature/session-auth`** — та сама авторизація, але на серверних сесіях
   (таблиця `Session` + sid у кукі). Не мерджити. Ціль — написати в README чесне
   порівняння з цифрами: скільки запитів до БД на кожен запит API, що складніше
   масштабувати, що простіше відкликати.
7. **CSRF — показати, а не прочитати.** Підніми `attacker.html` на іншому порту
   (`python -m http.server 5500`) з формою, яка POST'ить на твій `/auth/refresh`.
   - `SameSite=None` → атака проходить;
   - `SameSite=Lax` → ні;
   - прибери кукі взагалі, поклади refresh у localStorage → CSRF зникає, але зʼявляється XSS-вектор.
   Потім додай double-submit CSRF token і поясни, навіщо він, якщо є SameSite.
8. `express-rate-limit` на `/auth/login` і `/auth/refresh` — і аргумент, чому саме там.

### Маю пояснити
Stateless vs stateful auth і що кожен варіант коштує. Навіщо два токени. Чому
HttpOnly-кукі рятують від XSS-крадіжки токена, але відкривають CSRF, а
`Authorization` header — навпаки. Як відкликати JWT (і чому чесна відповідь —
«ніяк, потрібен стан»). Що робить token rotation і як ловиться повторне використання.

### Ресурси
- **The Copenhagen Book** — https://thecopenhagenbook.com — найкращий сучасний текст
  рівно по цьому списку (sessions, tokens, cookies, CSRF). Читається за вечір.
- **OWASP Cheat Sheets**: Authentication, Session Management, Cross-Site Request Forgery
  Prevention — https://cheatsheetseries.owasp.org
- **MDN: Set-Cookie і SameSite** — https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Set-Cookie
- Sven Slootweg, «Stop using JWT for sessions» — навмисне різкий текст; прочитай як
  опонента і сформулюй, де він правий, а де ні. Це готова відповідь на співбесіді.

## Блок 5 — CORS
**Фідбек: пункт 5**

Робиться разом із підключенням фронта (Day 6 у ROADMAP).

### Що роблю

1. **Видали пакет `cors`** і напиши свій middleware на 15 рядків: `Access-Control-Allow-Origin`,
   `-Methods`, `-Headers`, `-Credentials`, `Max-Age`, `Vary: Origin`, і відповідь `204` на `OPTIONS`.
   Оце і є «налаштувати CORS без прив'язки до фреймворку» з фідбеку.
2. **Зроби preflight видимим.** З фронта на іншому origin виклич:
   - `GET` без кастомних заголовків → preflight'а немає (simple request);
   - `PATCH` з `Content-Type: application/json` → preflight зʼявився.
   Подивись обидва в Network tab. Зрозумій, що список «simple» — це не логіка, а
   історична сумісність.
3. **Той самий запит у Postman** — працює. Сформулюй одним реченням, чому.
4. **Зламай навмисно:** `credentials: 'include'` + `Access-Control-Allow-Origin: *`.
   Прочитай помилку браузера і поясни, чому специфікація це забороняє.
5. `Access-Control-Expose-Headers` — віддай із бекенда кастомний `X-Total-Count` для
   пагінації і побач, що фронт його не бачить, поки не виставиш expose.

### Маю пояснити
Що CORS — це обмеження браузера, а не захист сервера (сервер усе одно має авторизувати).
Що таке origin і чим він відрізняється від домену. Навіщо preflight. Чому `Vary: Origin`
обовʼязковий, якщо між тобою і клієнтом є кеш/CDN.

### Ресурси
- **MDN CORS** — https://developer.mozilla.org/en-US/docs/Web/HTTP/CORS — читати повністю, воно того варте.
- **MDN: Preflight request** — https://developer.mozilla.org/en-US/docs/Glossary/Preflight_request
- Jake Archibald, «Who's afraid of CORS?» — пояснює, звідки взявся список simple requests.

## Блок 6 — REST, bulk-операції та асинхронність
**Фідбек: пункти 6 і 7 — вони природно робляться однією фічею**

### Що додаю в проєкт

1. **Аудит наявних ендпоінтів** проти ресурсного підходу. Чесно подивись на `/stats`:
   це ресурс чи RPC? Якщо RPC — це нормально, але ти маєш це усвідомлювати і вміти
   захистити.
2. **PUT проти PATCH по-справжньому.** `PUT /media/:id` — повна заміна (відсутнє поле
   означає «стерти»), `PATCH /media/:id` — часткове оновлення (JSON Merge Patch, RFC 7386).
   Питання: як у PATCH відрізнити «поле не передали» від «поле передали як `null`»?
   Зараз у тебе цей баг майже напевно є.
3. **Bulk-ендпоінт — серце блоку.** `PATCH /media/bulk` з тілом
   `{ ids: string[], status: Status }` на 50–500 елементів. Реалізуй **тричі**:
   - `Promise.all` → один невдалий елемент валить усе, інші продовжують виконуватись
     у фоні, а ти вже відповів 500. Побач це в логах;
   - `Promise.allSettled` → зібрати `fulfilled`/`rejected`, віддати `207 Multi-Status`
     з результатом по кожному id;
   - **одна транзакція** (`prisma.$transaction` / `updateMany`) → all-or-nothing.
   Потім відповідай на головне питання: **яка семантика правильна для цієї фічі** і
   що ти скажеш клієнту API при частковому успіху.
4. **Ліміт паралелізму.** Запусти bulk на 1000 елементів без обмеження і подивись на
   пул зʼєднань Prisma. Потім додай обмеження (`p-limit` або 20 рядків свого коду).
   Це і є місце, де `Promise.all` «працює, але ламається на масштабі».
5. **`Promise.race` і `Promise.any`** — реальний кейс у блоці 7: тягнути обкладинку
   з TMDb і RAWG паралельно, `any` = перший успіх, `race` + таймаут = запобіжник.
6. **Статус-коди в бою:** 201 з `Location` на create, 204 на delete, 409 на дубль
   (у тебе вже є `@@unique([userId, title])` з блоку 1), 422 vs 400 на валідації —
   обери один і будь послідовним. 202 на bulk, якщо винесеш у фон (блок 8).
7. **Формат помилки — RFC 9457 Problem Details** (`type`, `title`, `status`, `detail`,
   `instance`). У тебе вже є `AppError` і `errorHandler` — привести до стандарту.
8. **Zod** на всіх вхідних тілах (це і Day 5 з ROADMAP).

### Маю пояснити
Різницю 400 / 401 / 403 / 404 / 409 / 422 на прикладах зі свого API. Чому PUT
ідемпотентний, а POST — ні, і що ідемпотентність означає на практиці (retry після
таймауту). Поведінку всіх чотирьох комбінаторів Promise при 1 і при кількох reject'ах.
Коли bulk має бути транзакцією, а коли — частковим успіхом.

### Ресурси
- **Zalando RESTful API Guidelines** — https://opensource.zalando.com/restful-api-guidelines/
  — безкоштовні, дуже конкретні, з обґрунтуванням кожного правила.
- **RFC 9110 (HTTP Semantics)** — не читати цілком; секції про методи й статус-коди
  як довідник: https://www.rfc-editor.org/rfc/rfc9110.html
- **RFC 9457 Problem Details** — https://www.rfc-editor.org/rfc/rfc9457.html
- **MDN: Promise** — секція про combinators; плюс доповідь Jake Archibald «In The Loop»
  про event loop, якщо захочеш закріпити мікротаски.
- Документація Stripe API як еталон дизайну (особливо idempotency keys і формат помилок).

## Блок 7 — Інтеграції: email та реалтайм
**Фідбек: пункт 9**

### Що додаю в проєкт

1. **Верифікація email при реєстрації.** Токен (одноразовий, з TTL, у БД — знову
   хеш, не сам токен), лист із посиланням, `GET /auth/verify?token=...`.
   Це переюзає все з блоку 4.
2. **Nodemailer + Mailtrap або Ethereal** на дев. Подивись на сирий SMTP-діалог
   (`debug: true`) — EHLO, AUTH, MAIL FROM, RCPT TO, DATA. Один раз побачити варто.
3. **Потім переключи на Resend або Amazon SES** за одним інтерфейсом `EmailProvider`.
   Ось тут ти й отримаєш відповідь «SMTP vs API-провайдер» з власного досвіду.
   Побіжно розберись, що таке SPF / DKIM / DMARC і чому лист з твого VPS іде в спам.
4. **SSE для прогресу імпорту.** Зроби `POST /media/import` (CSV на 500 рядків) і
   `GET /media/import/:jobId/events` через Server-Sent Events.
   Спочатку **аргументуй письмово**, чому тут SSE, а не WebSocket (трафік односторонній,
   працює поверх звичайного HTTP, автоперепідключення з коробки). Потім реалізуй.
5. **GraphQL — не будувати.** Написати 5 речень: що він вирішує (over/under-fetching,
   один ендпоінт на багато клієнтів), чим платить (кешування, N+1, складність),
   і чому для цього застосунку програє REST.

### Маю пояснити
REST / GraphQL / WebSockets / SSE — чотири сценарії, по одному реченню кожен, без
«ну це щось типу». Чому свій SMTP-сервер ніхто не піднімає. Чим відрізняється
транзакційний лист від маркетингового (і чому Mailchimp — це інша категорія
сервісу, ніж SES).

### Ресурси
- **Nodemailer docs** — https://nodemailer.com
- **MDN: Server-sent events** — https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events
- **Resend або AWS SES docs** — обери один і прочитай quickstart + розділ про домени/DKIM.

## Блок 8 — Системний дизайн і аргументація рішень
**Фідбек: пункти 8 і 10**

Найважливіший блок, бо фідбек по суті каже: рішення були нормальні, **обґрунтування — ні**.

### Що додаю в проєкт

1. **`docs/adr/` — Architecture Decision Records.** Шаблон Майкла Найгарда:
   Context / Decision / Alternatives considered / Consequences. Мінімум 5 штук:
   - `0001-postgres-over-mongo.md`
   - `0002-cuid-vs-uuidv7.md` (з цифрами з блоку 2)
   - `0003-no-redis-yet.md` — **саме цей закриває докір про Redis без потреби.**
     Запиши конкретний поріг: «додаю Redis, коли p95 `/stats` > 300 мс при > N юзерів»
   - `0004-jwt-with-refresh-rotation-over-sessions.md` (з гілки в блоці 4)
   - `0005-react-spa-over-nextjs.md` — для цього застосунку: SEO не потрібне (дані
     приватні за логіном), SSR не дає нічого, окремий бекенд уже є. Напиши, за яких
     змін продукту рішення перевернулось би.
2. **Кешування — від болю, а не від моди.** Заміряй `/stats` на 200k рядків із блоку 2.
   Далі по черзі: (а) індекс/переписаний запит, (б) in-memory Map з TTL,
   (в) тільки тоді Redis. На кожному кроці — заміри. Окремо сформулюй, що ламає
   in-memory кеш при 2+ інстансах — це і буде твоя чесна відповідь «коли Redis».
3. **Object storage.** Аватар юзера і обкладинка: завантаження через **presigned URL**
   у S3 або Cloudflare R2, у БД лежить лише ключ. Твоє рішення «URL, не байти» у
   PROGRESS.md правильне — тепер маєш його реалізувати й уміти захистити (розмір рядка,
   TOAST, бекапи, CDN, окреме масштабування).
4. **Спостережуваність по-мінімуму:** структуровані логи (pino), `requestId` у кожному
   лозі, таймінг запиту. Без цього всі заміри вище — це `console.time`.
5. **Тести:** 5–7 інтеграційних на auth-флоу і bulk (Vitest + supertest, тестова БД).
   Reuse detection із блоку 4 має бути тестом.

### Маю пояснити
Для кожного компонента: яка вимога його викликала, який метричний поріг, і що буде,
якщо його не додати. Які дані належать БД, а які — object storage, і чому.
React vs Next.js для **цього** застосунку — і за якої зміни вимог відповідь інша.
